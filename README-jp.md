# Sakura プロジェクト構成

Sakura は、2 つのプロジェクトから構成される .NET ソリューションです。

- `MerkleTrees.csproj`: 基本的な Merkle ツリー実装と、特殊化された実装を提供するライブラリです。
- `ProofOfReserve.Api.csproj`: ユーザーの残高と、それに対応する Merkle プルーフを取得するための Web API です。

> 補足: さらに、それぞれに対応するテストプロジェクトもあります。

## MerkleTrees

MerkleTrees ライブラリは、Merkle ツリーの 2 つの実装を提供します。

このライブラリは、次の 2 つの主要クラスで構成されています。

- `MerkleTree.cs`: 基本実装
- `UserAccountMerkleTree.cs`: ユーザーアカウント向けに特殊化されたバージョン（クラスのドキュメントを参照してください）

このプロジェクトの**意味のあるテストデータ**は、`MerkleTreeTests.cs` の  
`Constructor_WithSpecificData_ShouldReturnAGivenMerkleRoot()` というメソッドにあります。

MerkleTrees プロジェクトのすべてのテストを実行するには、ルートディレクトリから次のコマンドを実行してください。

```bash
dotnet test tests/MerkleTrees.Tests/MerkleTrees.Tests.csproj
```

### 依存関係

このプロジェクトは**サードパーティ製ライブラリを使用していません**。テストフレームワークとしては xUnit を使用しています。

## Proof of Reserve API

この Web API は、次の 2 つの機能を公開しています。

1. ユーザーとその残高のリストを登録する
2. 特定ユーザーの残高と、それに対応する Merkle プルーフを取得する

このプロジェクトでは、`MerkleTree.cs` を特殊化した実装を使用しています。  
その目的は、ユーザーの残高および追加データを含む Merkle プルーフを返すことです。

新しいバージョンのライブラリで追加された主要なメソッドは `GetMerkleProof()` です。

### 依存関係

この Web API プロジェクトでは、Controller ベースの API の代わりに [Minimal APIs](https://learn.microsoft.com/en-us/aspnet/core/tutorials/min-web-api) を使用しています。  
これは、API ベースのプロジェクトで依存関係を最小限に抑えるための方法です。

そのため、このプロジェクトのランタイム依存関係は ASP.NET Core 共有フレームワークのみです。

これに加え、テストフレームワークとして xUnit を使用していますが、**サードパーティ製ライブラリは使用していません**。

## 追加設定

`MerkleTrees.Tests.csproj` と `ProofOfReserve.Api.Tests.csproj` の両方に含まれる設定ファイル `xunit.runner.json` は、xUnit のテスト出力で文字列が切り詰められるのを防ぎます。主に、開発中のデバッグを容易にするために使用されています。

`.editorconfig` のルールは、慣用的な .NET の規約に従うように選定されています。

## 1. Merkle ルートの計算

MerkleTrees ライブラリは CPU バウンドな処理を行い、I/O は行いません。

このライブラリの最初のバージョン（Merkle ツリーの基本実装のみを含むもの）の完成時に作成された Git タグは、[v1.0](https://github.com/Gregordy/Sakura/releases/tag/v1.0) です。

`MerkleTreeTests.cs` には、そのためのテストが含まれています。

### スケーラビリティに関する考慮事項

以下は、各操作の時間計算量の内訳です。

1. ツリーの構築には `O(n)` の時間がかかります。線形個数のノードをハッシュ化するためです。
2. Merkle プルーフの生成は `O(log n)` の操作です。ツリーの高さをたどる必要があるためです。
3. 最後に、すべてのリーフに対するプルーフの生成は `O(n log n)` です。各プルーフがそれぞれ独立してツリーをたどるためです。

ツリーが一度構築されれば、Merkle ルートの取得は定数時間の操作です。

## 2. Proof of Reserve Web API

Proof of Reserve Web API は、`ProofOfReserve.Api` フォルダーにあります。

更新された MerkleTree 実装（**UserAccountMerkleTree.cs**）に対する新しい Git タグは、[v1.1](https://github.com/Gregordy/Sakura/releases/tag/v1.1) です。

### API の起動

Proof of Reserve API を起動するには、次のコマンドを実行します。

```bash
dotnet run --project src/ProofOfReserve.Api/ProofOfReserve.Api.csproj
```

API は `http://localhost:5066` で起動します。

### API のテスト

> 注意: 機能は 2 つだけです。1 つは GET を使用し、もう 1 つは POST を使用します。どちらも `/users` エンドポイントを使用します。

API を起動すると、`ProofOfReserve.Api/Program.cs` でシングルトンとして登録されたインメモリデータベースが起動します。

次の POST リクエストでデータを登録（シード）してください。

```http
POST http://localhost:5066/users
Content-Type: application/json

{
  "users": [
    { "id": 1, "balance": 1111 },
    { "id": 2, "balance": 2222 },
    { "id": 3, "balance": 3333 },
    { "id": 4, "balance": 4444 },
    { "id": 5, "balance": 5555 },
    { "id": 6, "balance": 6666 },
    { "id": 7, "balance": 7777 },
    { "id": 8, "balance": 8888 }
  ]
}
```

このリクエストは、次のレスポンスを返します。

```json
{
  "merkleRoot": "b1231de33da17c23cebd80c104b88198e0914b0463d0e14db163605b904a7ba3"
}
```

特定のユーザーに対する Merkle プルーフと追加データを取得するには、次のリクエストを使用します。

```http
GET http://localhost:5066/users/1
```

> 注意: ここでの `1` は、Merkle プルーフを取得したいユーザーの ID です。

このクエリに対するレスポンスは次のとおりです。

        "siblingPosition": 1

## 3. 改善のための提案

Proof of Reserve Web API を実際のサービスとして提供する場合、多くの改善を検討する必要があります。

### セキュリティ

a) **認証**

API への不正アクセスを防ぐため、API トークンまたはユーザーアカウントのいずれかを要求することが望ましいです。

また、特定のユーザーがどのデータにアクセスできるかを判断するための認可ルールも適用する必要があります。

b) **入力データの検証**

現在、入力データの検証は限定的です。

実際の本番サービスでは、適切な検証とリクエストサイズの制限を設けることで、無効な入力、過剰なリソース消費、および潜在的なセキュリティ脆弱性を防ぐことができます。

この API では、1 回のリクエストで作成できるユーザー数を制限することで、過度に大きな処理を防ぐことができます。

c) **レート制限**

この Web サービスは公開されるため、悪用や過剰なトラフィックに対して脆弱になります。

このような悪用を防ぐためには、クライアントが一定期間内に実行できるリクエスト数を制限する必要があります。

### データ整合性

a) **長期的な永続化**

現在、データベースはインメモリです。

そのため、サービスを再起動したり、クラッシュしたりするたびにデータは失われます。これを防ぐには、インメモリデータベースを永続ストレージに置き換えることができます。

b) **同時実行性と整合性**

同時リクエストによって、異なるバージョンのユーザーデータを表す Merkle ルートやプルーフが生成されてはなりません。

これを防ぐには、ツリーの更新をアトミックに適用する必要があります。また、プルーフの生成は、一貫したツリーのスナップショットに対して行う必要があります。

現在のインメモリ実装では、同期が必要になる場合があります。  
永続ストレージを導入する場合は、整合性の要件に応じて、適切なトランザクションおよび分離戦略を検討する必要があります。

### スケーラビリティ

a) **キャッシュ**

ツリーが変更されていない場合にプルーフを重複して計算しないようにするには、キャッシュが有効です。  
リクエスト間で新しいユーザーが追加されていない場合に、ツリーを再構築しないようにする場合も同様です。

ただし、キャッシュは、パフォーマンス測定によって意味のある効果が確認された場合にのみ導入すべきです。

キャッシュされたプルーフや Merkle ルートが、基盤となるユーザーデータと一貫性を保つように、キャッシュの無効化は慎重に扱う必要があります。

b) **増分的なツリー更新**

現在、Merkle ツリーはリクエストされるたびに完全に再構築されています。

ツリーがある程度のサイズを超えて成長した場合、増分的なツリー更新の実装を検討すると有益になる可能性があります。

### 保守性

a) **より堅牢なエラーハンドリング**

現在、エラーハンドリングは最小限です。

デバッグを容易にし、システムの可視性を高めるためには、重複するユーザー ID、存在しないユーザー、無効なリクエストデータ、その他予期される失敗状態を正確に処理し、エンドユーザーに意味のある情報を提供する必要があります。

b) **永続化の抽象化**

永続化処理をビジネスロジックからより明確に分離するための抽象化レイヤーを追加することで、将来的にアプリケーションが異なるストレージプロバイダーをサポートする必要が生じた場合の保守性と拡張性が向上します。

### API 設計

現在、POST エンドポイントは 2 つの処理を行っています。

- 提供されたデータからユーザーを作成する
- 新しく作成されたユーザー（および既存のユーザーがいる場合はそれらも含む）全体に対する Merkle ルートを返す

これらの機能は、次のように**異なるエンドポイントに分割する**方が望ましいです。

- `POST /users`: ユーザーの作成のみを処理し、成功時には HTTP 201、失敗時には 400 を返す
- `GET /users/{userId}/balance`: 指定されたユーザーの Merkle プルーフを返す
- `GET /users/summary`: 現在保存されているすべてのユーザーに対する Merkle ルートを返す

さらに、OpenAPI を統合することで、API の利用、保守、ドキュメント化が容易になります。
